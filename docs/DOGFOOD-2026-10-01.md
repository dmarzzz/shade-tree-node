# Dogfood run, 2026-10-01

Using ShadeNet v0.7.0 the way an agent operator would, on the staging canopy, and writing down
every piece of friction. No ETH was spent and no seat was staked or sponsored; the seats used were
the ones the M7 and H1 rehearsals left in the staging set `0xf117…7B7E`.

Setup facts that shaped the run:

- The fleet (both Elders, nodes 04/05/06) was rolled to v0.7.0 against the **production** set
  `0xDEB2…4bBC` at M8, which has no members. Staging seats are therefore refused
  `gate:wrong-group-root` by every node. For this run node-06 got a temporary systemd drop-in that
  adds the staging set to `SHADE_TREE_GROUP_CONTRACT` (per-contract start blocks through
  `SHADE_TREE_FROM_BLOCKS`), so one node in three admitted the staging seats. The drop-in file
  was removed afterwards; the running gateway keeps the setting until the next fleet roll.
- The orbital-one Hermes client was pointed back at the staging record (agent-devops #31); it was
  on the bundled production network and `not_admitted`.
- Seats: the H1 rehearsal identity (tier 1) from halcyon; the Hermes client leaf on orbital-one
  (tier 1); the SearXNG stack identity on orbital-one (tier 8, image `shadenet:dev-694ddd0`).

| `init --network <staging record>` (fresh `$HOME`) | 31 s | identity, token, config written; prints the bond as `1000000000000000 wei` | Tor bootstrap + canopy fetch on every command (#236); wei (#239); no way to name a non-bundled network except a path |

wall clock, of which about 3 minutes were commands bootstrapping Tor.

## 2. Hermes on orbital-one: 10 fetches in a burst

`hermes chat --oneshot` with the `shadenet` MCP server (tier-1 seat, tickets on). 7 tool calls,
73 s, then Hermes stopped and told the user to resume in 59 s.

| URL | Result |
|---|---|
| api.ipify.org | `node_refused`: `2kuu… refused: wrong-group-root` (16.7 s) |
| the other nine | `budget_exhausted`, `retryAfterSeconds: 23`, each returned in 0.1 s |

The one refused dial spent the epoch's slot; the model did not wait for the reset (#232, #233,
#235). The Hermes skill tells the model to wait `retryAfterSeconds`; it did not.

## 3. SearXNG through the canopy: 20 searches over 10 minutes

JSON API at `127.0.0.1:8090` (the stack's `SEARXNG_PORT`; 8080 is another service on that box).

| Phase | Searches | 200 with results | Latency | Engines |
|---|---|---|---|---|
| before the proxy restart (06:05–06:09Z) | 7 | 7 | p50 19.9 s, p95 20.1 s, one at 6.0 s | results from `google cse` only; `brave` "too many requests", `duckduckgo` timeout or captcha on every query |
| after `docker restart searxng-shadenet-1` (06:09:34Z) | 13 | 0 | connection refused in 0.05 s | SearXNG's network namespace died with the proxy container |
| after `docker restart searxng-searxng-1` (06:16:14Z) | back in 14 s | 200 | 0.5 s | the routed engines are now "Suspended", so nothing goes through ShadeNet |

The 20 s latency is SearXNG's `request_timeout` waiting for the routed engines, which never
delivered a result: the proxy container (an older build) logged 12 `refused: gate` and two nodes
failing, and brave rate-limits the shared node IP. Once SearXNG suspends those engines, searches are
fast but unprotected (#237).

## 4. Claude Code through the proxy

Two paths.

`shadenet run --no-proxy api.anthropic.com -- claude -p …` (scoped environment): the child got
`NO_PROXY=…,api.anthropic.com` and `NODE_USE_ENV_PROXY=1`, yet Claude Code's own startup went
through ShadeNet: 14 CONNECTs refused `budget_exhausted` in 4 s, then the next epoch's session
book spent tickets 0–4 on `api.anthropic.com`, `mcp-proxy.anthropic.com` and
`http-intake.logs.us5.datadoghq.com` before any user fetch (#230). The model then declined the
task because the prompt carried a proxy credential; that was a prompt mistake (the token is
already in `HTTPS_PROXY`), but it shows the scoped-environment path needs a recipe that never
shows the agent a credential.

`claude -p --mcp-config` with `shadenet mcp` (28 s end to end): `shadenet_status` ok, then
`api.ipify.org` → `transport: all 1 candidate(s) failed` (15 s), and the four remaining URLs →
`budget_exhausted`, `retryAfterSeconds: 37`. The model summarised and stopped (#232, #233, #235).

## 5. Restarts mid-task

| What | Seen by the agent |
|---|---|
| kill and restart the local proxy during a curl loop | 4 s gap; the request in flight got no HTTP answer (`000`), the next request succeeded in 19.6 s; nothing in the error says "proxy restarted" |
| restart the SearXNG stack's proxy container | SearXNG unreachable until its own container is restarted (#237) |
| restart a node | not done: the single node-06 restart allowed was used to admit the staging set |

Also seen in this epoch: the second curl after a successful one, in the same epoch, was refused
`budget_exhausted: used 1/1 tunnels` although the session book opened for the first one still had
five tickets (#231). Sequential clients get one fetch per minute even with tickets on.

## 6. Can an agent act on the errors?

| Surface | What it said | Actionable? |
|---|---|---|
| `shadenet status --json` after refusals | `state: ready`, `lastError: null` | no (#234) |
| `/_shadenet/status` | same | no |
| `shadenet doctor` | ten `ok` lines | no: it checks the local half only (#234) |
| proxy CONNECT refusal | JSON body + `X-ShadeNet-Error`, but `curl -w %{http_code}` shows `000` | partly; documented now (#240) |
| MCP errors | `code`, `retryAfterSeconds`, a one-line message | yes, but both models ignored `retryAfterSeconds` (#235) |
| `node_refused` body | names the onion and `wrong-group-root`; ERRORS.md said it "clears on retry" | misleading; fixed here |

Operator-side note, not filed: a gateway can admit several sets (`SHADE_TREE_GROUP_CONTRACT`
is a comma list, `SHADE_TREE_FROM_BLOCKS` per contract), but neither the record nor the v4 role
can express it, so the staging and production canopies cannot coexist on one fleet without a
hand-written drop-in. OPERATOR-JOIN may want a `sets[]` in the record.

## Doc fixes landed with this report

AGENT.md says "staked", not "paid", and names the ceremony; ERRORS.md explains
`wrong-group-root` and how to see a refusal from curl; the SearXNG README says to restart both
services together.
